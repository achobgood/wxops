One trap worth recording for the next run: a spec_sync run that gets as far as
refreshing the name lock WRITES the then-current names into
tools/command_name_lock.json. If you then rename anything, the next run's lock
refresh refuses against your own provisional names. Reset the lock to
origin/main before re-running, or the refusal list is noise.

# Routing decisions — spec-sync 2026-09-28

Five new command groups appeared in this refresh. One line each, per contract §2 B.

- call-controls-members -> call-control (Cisco tagged the member-scoped wrap-up-reason POST apart from Call Controls, but it is a Calling call-control action on a live call, which is exactly this skill's surface; the WxCC `cc-aux-code` lookalike belongs to contact-center and is called out in both the skill and the CLAUDE.md row)
- call-controls-members-me -> call-control (same operation, self-scoped; splitting the pair across skills would make the token-scope choice invisible at the point of use)
- external-data-updates -> contact-center (PUT /v1/data/updateExternal writes global-variable values onto handled CC contacts; the variable definitions it depends on are `cc-global-vars`, already routed to this skill, and it needs the region-scoped CC base URL plus `cjp:` scopes that only this skill sets up)
- user-call-settings-members -> manage-call-settings (voicemail MESSAGE state — summary, list, mark read/unread, delete; this skill already owns per-person voicemail, and the adjacent `user-settings` voicemail CONFIG commands are the thing users will confuse it with, so the disambiguation belongs in the same skill rather than across two)
- user-call-settings-members-me -> manage-call-settings (self-scoped twin of the above; routed together for the same reason as the call-controls pair)
