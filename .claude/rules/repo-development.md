# Repo development — source repository only

For maintainers changing `wxcli`, its generator, its tests or its packaging. This rule is excluded from the shipped playbook (`wxcli-dist/assemble.py` `EXCLUDE_FILES`), so a customer folder never loads it. Generator rules, the drift gate and the regen workflow are in `tools/CLAUDE.md`.

## Running the tests

One command, for the whole merged repo (wxcc-agent-builder's tests included):

```bash
venv/bin/python -m pytest <the test files your change touches> -q
```

- **Interpreter:** `venv/` is a Homebrew Python 3.14 venv at the repo root: `/opt/homebrew/bin/python3.14 -m venv venv && venv/bin/pip install -e . pytest pytest-asyncio aioresponses pyyaml`. A git worktree gets its own `.venv/` the same way: the editable install reads `wxcli` from the tree it was installed in, so a shared venv tests the wrong code. `PYTHONPATH=.` does not fix that: it makes `tools/` local to a clone, but `tools/command_renderer.py` imports `wxcli.common`, so a clone that runs another tree's venv regenerates with that tree's `src/wxcli` and silently ignores the clone's own edits, with exit 0 and no warning (measured 2026-08-05). Install the clone into its own venv.
- **Targeted, not the full suite.** Name the files. `venv/bin/python -m pytest tests/ -q` runs the whole default suite and is slow; say so before running it. A full run needs `venv/bin` on `PATH` (`PATH="$PWD/venv/bin:$PATH"`), because a test shells out to `wxcli`.
- **After a regeneration, also run the tests that check the output against something else**, not only the tests for the module you changed: a regenerated file can be right while a consistency test beside it breaks (wxcc's Codex port, 2026-07: the bundle's own tests passed and a mirror test failed). Commands (`tools/generate_commands.py`, `tools/command_renderer.py`, `tools/field_overrides.yaml`): `tests/test_generate_commands.py tests/test_generator_regression.py tests/test_field_overrides.py` and the drift gate. `tests/test_generator_regression.py` snapshots rendered output; on 2026-10-14 about 1,150 targeted tests passed, then CI's full suite failed on that one snapshot (update it with the recipe in its docstring). The playbook bundle (`wxcli-dist/assemble.py`): `tests/wxcc/test_assemble.py tests/wxcc/test_context_layout.py tests/wxcc/test_doc_consistency.py`. When such a test has to learn about a new generated file, add that file to a narrow allow-list, never a rule that ignores any file without a source.
- **Before tagging a release,** push to `main` and read CI: CI is where the full suite runs.
- **To check whether a failure predates your change,** check out the base commit in a worktree. `git stash` cannot set aside a change that is already committed.
- **Never search rendered `--help` text in a test.** Rich colour codes split the words, so a substring check fails or passes by accident. Inspect the parameters instead: `typer.main.get_command(app)` (as `tests/wxcc/test_init_playbook.py` does).
- **Tiers are opt-in.** The default run excludes them (`pyproject.toml` `addopts = "-m 'not live and not mutation'"`). `-m live` calls the real Webex API with your token. `-m mutation` creates, changes and deletes resources in a live org and runs only with `WXCLI_LIVE_MUTATION=1` set as well (flows named `CLITest_WebexOps_*`, deleted in teardown). Never run either without being asked. Reads passing says nothing about writes: a new command group is tested through create → verify → update → verify → delete → verify in a live org before anyone relies on it (in March 2026, three bugs in the first version showed up only that way).
- **CI** runs `pytest tests/ -m "not live and not mutation"` on Python 3.11 and 3.12 (`.github/workflows/ci.yml`). `pyproject.toml` requires Python 3.11 or later.
- **Never bare `python3`.** On macOS it is Apple's Python 3.9.6. wxcc recorded (2026-07-27) that `python3 -m pytest -q` there silently under-tested: `tomllib` exists only from 3.11, `pytest.importorskip("tomllib")` skipped tests, and one that vanished was the guard that the shipped MCP config uses `bearer_token_env_var`, never a static token. Checked 2026-10-20: the two `importorskip("tomllib")` calls survive in `tests/wxcc/test_assemble.py` (lines 405 and 427), but that module also imports `tomllib` at line 10, so on 3.9 it now fails to collect instead of skipping; and `/usr/bin/python3` on the maintainer's Mac has no pytest at all. The failure is loud now. Use the venv anyway.

## Working in this repo

These rules came from the maintainer's private notes (Plan 6, 2026-10-20). Each one cost a real incident first.

- **Stage files by name.** Never `git add -A` or `git add .`: gitignored folders (`docs/prompts/`, `docs/superpowers/`, `docs/plans/`, top-level `tests/`) were re-tracked that way several times. Read `git status` against `.gitignore` before staging.
- **What is tracked.** Top-level `tests/*` is ignored by default (`.gitignore` § Tests); `tests/migration/`, `tests/wxcc/`, `tests/org_health/` and the named artifact guards are carved back in. Before committing a new top-level test, run `git check-ignore -v` on it: carving one in is a decision (it then runs in CI), not a way around the ignore. `.github/` is ignored except its three workflows; `ci.yml` has been tracked since 2026-07-14, because the drift gate in CI is what catches dead commands in the reference docs.
- **Count from git, never from disk.** Any count in any document, internal or public (command groups, skills, docs, specs, operations), comes from `git ls-files` or `git show HEAD:<file>`. The working tree holds gitignored files: on 2026-08-04 an audit counted them, reported wrong totals, and wrote a finding that a correct `CLAUDE.md` was wrong. Run `git check-ignore -v` on anything surprising. An assumption you could not confirm blocks every finding that depends on it.
- **Decisions go in a tracked `CLAUDE.md` next to the code** (`tools/CLAUDE.md` for the generator and the CLI surface), not only in a commit message or a plan under `docs/superpowers/` (gitignored). Record the rejected options and why, and say so when something that looks deliberate is a historical accident. On 2026-07-25 the reason `--output` existed on only some command types survived only in a four-month-old commit message, and it took a full investigation to learn it was an accident.
- **Never call a generated command function from Python.** The functions in `src/wxcli/commands/*.py` make real HTTP calls. Importing one skips the safety gate (it inspects Bash only), the confirmation prompt and the read-only policy. On 2026-07-28 a script called four generated `delete` functions with what it thought was `force=False`; a Typer default is an `OptionInfo` object, which is truthy, so the prompt was skipped and four unconfirmed DELETEs reached live endpoints, one of them the whole organization. Webex refused all four. Learn what a command does by reading its source (the URL, method and confirm text are literals); if some layer must run, monkeypatch the HTTP layer before any call; `--help` is safe. A brief for an agent says "static analysis only — never invoke a generated function".
- **Write `wxc[l]i` in search patterns.** The safety gate reads the whole Bash text, so a grep, awk or sed pattern that contains the CLI's name followed by a word can be refused although nothing runs it (2026-10-20). The bracket form matches the same text. Or put the script in a file and run `awk -f`. Text that names a Python import of the package goes in a file written with the Write tool, never in a heredoc.
- **Hook edits reach new sessions only.** Claude Code reads the hook configuration when a session starts: after an edit to `.claude/settings.json`, a subagent spawned afterwards uses the new hooks and the running session keeps the old ones (verified 2026-07-15). Test a hook change in a fresh subagent with a command it must refuse, or pipe a sample payload into the script, as `tests/test_wxcli_gate.py` does: `printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<command>"}}' | sh .claude/hooks/wxcli-gate.sh`. PreToolUse hooks still fire in `bypassPermissions` mode. A hook whose path does not resolve fails open, with no error, so pin any path change with a refuse-case test.
- **Before writing "there is no command for X",** scan every group in `wxcli --help` and grep `src/wxcli/commands/` for the API path or a body key: commands are named from the spec's operation IDs, so a feature can sit in a group whose name gives no hint (a person's monitoring settings are `person-call-settings list` and `update`, which a doc once said did not exist). Before writing "this never existed", run `git log -S "<symbol>" -- src/`, not only against `specs/`: on 2026-07-14 two hand-written commands were called fabricated, when a routine regen had deleted them two days after they were written.
- **Judge the CLI the way an agent uses it** (Adam, 2026-07-27: an LLM uses this CLI, not a person at a keyboard). Help text is scored on whether an agent builds the call right the first time and whether every argument names the command that produces its value. An error names the literal next command. `-o json` output is clean on stdout, because one stray banner byte breaks a parse. The naming trap is a command that runs but answers a different question (the Calling and Contact Center words: queue, team, site, dial plan, business hours, workspace, recording). Report latency multiplied out over 50, 200 and 1,000 calls. Token cost is a defect class, but never cut a doc on size alone: a shorter doc that drops a gotcha is worse.
- **A skill that names `wxcli` commands carries a `--help` gate** in its checkpoint section: "MANDATORY: Before including ANY wxcli command in your plan, verify it exists. Run `wxcli <group> --help` to confirm the command group exists and list its commands." Put Quick Recipes with exact commands before the step that loads reference docs, because a reference file name primes a wrong group name (`location-call-settings-advanced.md` led agents to invent `location-call-settings`). In six experiments on 2026-04-17, warnings, recipes and file renames all failed to stop invented command names; only the gate worked.
